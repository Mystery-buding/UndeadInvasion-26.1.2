# 2026-11-08

## 修复：第 10 天穿墙索敌后不会绕路破门（已完成，实证通过）

- 用户现象：亡灵能直接索敌屋内村民，但不绕到门口、不破门。
- 现状核对：压缩前的会话已写过一版 `SiegeBreakDoorGoal`（自建骑手体型 `GroundPathNavigation` 找路线上的木门 → 靠近 → 骑兵门口下马 → `super.tick()` 拆门），`ZombieSiege` 用 `keepOnFoot/shouldStayOnFoot` 防止进门期间重新上马；旧的 `SiegeDismountGoal` 已删除并合并进破门目标。
- 本次定位到的两个真实场景失效点：
  1. `findDoor` 要求 `Path#canReach() == true`。门关着、屋内有台阶/地毯/内墙时，`PathFinder.findPath` 返回的是「起点→最接近目标节点」的**部分路径**，`reached=false`（`PathFinder` 122–128 行），于是一扇门都找不到，目标从不启动。原版 `DoorInteractGoal#canUse()` 本来就不要求 canReach，只要求 `horizontalCollision` + 当前路径里有门节点。
  2. `tick()` 每 20 tick 重算一次路线，`findDoor` 返回 null 就直接 `finished=true`；站到门口后路径只剩一两个节点、门节点常消失，会把正在进行的 240 tick 破门进度打断。
- 修法（`gameplay/ai/SiegeBreakDoorGoal.java`）：
  - `findDoor` 去掉 `canReach()` 检查，只要求路径非空且包含关闭木门节点；路线不含门（普通墙、空房子）仍不触发。
  - `findFootRoute` 加 `setMaxVisitedNodesMultiplier(2.0F)`，避免 32 格索敌范围内绕村庄时节点上限截断路径。
  - `tick()`：仅在**接近阶段**重算路线；`breaking` 阶段完全不重算。只有明确找到**另一扇门**才终止；`findDoor == null` 只累计抖动次数，连续 3 次才放弃（`MAX_MISSING_ROUTE_SCANS`）。
  - `moveToDoor(Path)` 复用重算出的路径，接近阶段每次少算一次寻路。
- 测试（`src/gameTest/.../ZombieSiegeGameTests.java`）：新增 `door_is_broken_when_route_is_unreachable` —— 门后 z=11 再砌一道墙，寻路只能到门口（部分路径），验证仍会走到门口并把门拆掉、且保留村民目标。
- 验证：`JAVA_HOME=D:/Java/Java25.0.4 ./gradlew build -Dhttp.proxyHost= ...`（绕过全局代理）→ `BUILD SUCCESSFUL`，`runGameTestServer` **103/103 tests passed**，`zombie_siege` 环境 6/6 通过。原有 5 个攻城用例（骑兵绕门破门进屋、空房子不破门、普通墙不下马、室外追击保留坐骑、无攻城时仍可自动上马）均未回归。
- `CHANGELOG.md` 的 0.0.3 空章节已补上本次修复说明。

### 26.1.2 API 事实（本次核对）

- `Mob#getNavigation()` = `getControlledVehicle() instanceof Mob riding ? riding.getNavigation() : this.navigation`，骑乘时返回**坐骑**的寻路器；马是 `GroundPathNavigation#canNavigateGround() == true`。
- `WalkNodeEvaluator.getPathTypeWithinMobBB`：`DOOR_WOOD_CLOSED` + `canOpenDoors()` + `canPassDoors()` → `WALKABLE_DOOR`；`NodeEvaluator.canPassDoors` 默认 true。自建 `GroundPathNavigation` 必须 `setCanOpenDoors(true)` 才能把关闭木门算进路线。
- `PathNavigation` 构造的 `maxVisitedNodes = floor(FOLLOW_RANGE * 16)`；`createPath(Entity, reachRange)` → `createPath(Set<BlockPos>, 16, true, reachRange)`，目标点不扩展。
- `DoorInteractGoal` 用 `new BlockPos(node.x, node.y + 1, node.z)` 定位门；路径节点 `getNodePos(i)` 的当前格本身即可命中门方块，`isClosedWoodenDoor` 可先短路，不会因非门方块取 `OPEN` 属性抛异常。
- `BreakDoorGoal` 父类字段 `breakTime / lastBreakProgress / doorBreakTime` 是 protected，可直接在子类读写；`start()` 会重置 `breakTime`，故只在 `breaking=true` 时调一次 `super.start()`。

## 用户反馈「进游戏卡住」→ 攻城寻路性能优化（已完成）

- 证据：`run/gameTestServer/logs/latest.log` 11:17:11 出现 `Can't keep up! Running 2199ms or 43 ticks behind`；用户已自行把 `gradle.properties` 的 `mod_version` 改成 `0.0.3`（jar 为 `UndeadInvasion-26.1.2-0.0.3.jar`）。客户端日志是 11-04 的旧文件，没有本次真实游戏日志。
- 定位：上一轮把 `findDoor` 的 `canReach()` 放宽后，**任何**路径里带关闭木门的僵尸都会启动破门目标；每只僵尸每 20 tick 跑一次 `findFootRoute()`（32 格 A*），`setMaxVisitedNodesMultiplier(2.0F)` 又把节点上限从 560 放到 1120，`PathNavigationRegion` 半径 `maxPathLength + 16 = 48` → 7×7=49 个区块引用；`canUse()` + `tick()` + `start()` 一轮最多 3 次寻路。野外/村庄几十只亡灵同时做就会超 50ms/tick。
- 排除项：`DayCounterData.advance` 每 24000 tick 才触发 `resyncLoaded`；`PathNavigationRegion` 用 `getChunkNow` 不同步读盘；盾牌/投射物免疫 AI 是每 tick 小半径查询，量级低得多。
- 修法（仍只在 `SiegeBreakDoorGoal.java`）：
  - `findFootRoute` 的 `setRequiredPathLength` 改为 `min(siegeRange, max(8, 到目标距离 + 6))`，`setMaxVisitedNodesMultiplier` 恢复 `1.0F`。
  - 新增全局每游戏刻预算 `PER_TICK_SCAN_BUDGET = 4`（静态 `scanBudgetTick/scanBudgetUsed` + 同步块），`canUse()` 领不到额度就错开 20–39 tick 重试。
  - 路线里没门 / 门离目标超过 16 格 / 不允许破坏 → `nextScan = now + NO_DOOR_SCAN_INTERVAL(100)` 退避，不再每秒白跑 A*；找到门才恢复 20 tick。
  - 门与目标距离上限 `MAX_DOOR_TARGET_DISTANCE_SQR = 16²`，只拆目标所在建筑的门，避免拆路上路过的门（也减少无意义的 start/stop 震荡）。
  - 靠近阶段重算间隔 `APPROACH_REPATH_INTERVAL = 40`（探索性扫描仍 20）。
- 验证：再次 `./gradlew build` → `BUILD SUCCESSFUL`，103/103 game tests passed（`zombie_siege` 6/6），本次日志未再出现 `Can't keep up`。
- 未确认：用户没说明「卡住」是加载界面阶段还是进世界之后；上述修复只针对进世界后的服务端主线程负载。若仍卡，需索取整合包 `latest.log` / `crash-reports` 再判断。
